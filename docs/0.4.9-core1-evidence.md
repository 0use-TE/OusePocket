# 0.4.8 崩溃现场推理与待构建的 0.4.9 诊断修正

状态：已保留并离线解析 0.4.8 的完整复现现场。Wi-Fi 隔离改动已全部撤回，保持开启。0.4.9 在本次证据基础上增加早期总线/缓存状态采集和内部堆转储过滤；构建和设备验证结果见文末。不再生成额外固件包。

## 这次现场证明了什么

附件 3fb6065a-c910-453d-b3cf-a9916ab260a3 与完整 SHA256 为 `63f5c5e97fbae9b87275c0e617b90d19e0f0f0318689137ca72abf438b2b47ba` 的 ELF 匹配。副本位于 `.tools/diagnostics/63f5c5e97/`。

发生在 Core1，MCAUSE=7（Store access fault），MEXSTATUS=0x00102130，BUS_ERR=1、PMP_ERR=0、FETCH_ERR=0。这是总线错误类别，未指示 CPU PMP 违规，不能由此排除其他总线访问控制或宣称硬件损坏。

有效历史中的三条写入，经匹配 ELF 反汇编，均为正常函数栈保存：

| 由旧到新 | 指令 | 真实地址 | 含义 |
| --- | --- | --- | --- |
| STORE2，PC 0x4ff36056 | sw a4,8(sp) | 0x4ff42c78 | Tick 例程保存寄存器 |
| STORE1，PC 0x4ff3488e | sw ra,28(sp) | 0x4ff42c6c | 临界区函数序言保存返回地址 |
| STORE0，PC 0x4ff34898 | sw s0,24(sp) | 0x4ff42c68 | 同一函数序言保存寄存器 |

原始异常 PC=0x4ff3489c；SDK 打印 PC=0x4ff36056，确实改成了最早历史失败指令，说明不能仅凭标准 MEPC 解释现场。

MAP 中 xIsrStack 起点 0x4ff41c50，大小 0x1060；每核 2096 字节。因此 Core1 中断栈为 `[0x4ff42480, 0x4ff42cb0)`。三个真实写地址和 SP=0x4ff42c50 均在该区域且满足对齐。失败发生在进入临界区函数的前几条栈保存指令，尚未执行随后的锁对象读取；目前没有“失效互斥锁句柄”的直接证据，也没有直接栈越界证据。

PMP 第 6 项是 TOR、读写允许，其区间为 `[0x4ff3b180,0x4ffc0000)`，覆盖上述栈；与 PMP_ERR=0 一致。权限原值已保存，不能因开启 JTAG 后不复现就排除权限/时序因素：本地 SDK 在检测到调试器时会改变 IRAM/DRAM 的 PMP 布局。

## 候选原因如何排序

当前证据优先指向 CPU 对内部 SRAM 的写入路径出现总线异常：底层 SDK/芯片版本适配、总线/缓存/访问控制状态，以及供电或时钟稳定性都需要调查。正常地址的存储被拒绝，不能由普通 JS 控件数据损坏直接解释；但软件或驱动仍可能间接改变底层状态，未被排除。

ESP-Hosted/Wi-Fi 是有效候选或负载触发因素，不能凭“加入后问题增多”定为根因，也不能凭错误栈不含 Wi-Fi 就排除它。需要结合完整转储中的另一核心任务、NVS/Flash、LVGL 与 SDIO 活动，查找发生时的共享状态；目前不直接关闭服务或修改 SDK 调度器。

前序 Wi-Fi 固件版本查询超时与本次访问异常须分开：这次 Station 和扫描已完成，原先初始化门槛已越过，协议版本警告本身尚不能解释内部 ISR 栈的连续总线写错误。

## Received 计数与实际设备状态

用户确认计数持续增长，这是监视器接收并隐藏 Base64，不是据此可判定的死循环。0.4.8 的 IDF 6.1 heap walker 包含 PSRAM，115200 下数 MB 输出会持续数分钟。用户关闭监视器后进行八秒只读监听，没有新数据；随后只读 HELLO 收到 `core=0.4.8,storage=ready,...`，证明板子当时已离开转储并能响应协议，不是靠本轮复位恢复。

监视器处于接收阶段时数据保存在进程内存，完成后才处理临时 core 文件。未收到 END 就关闭可能丢失完整转储；下一次应直接保存原始串口字节，或完整保留 monitor 解析结果。

## 烧录与 JTAG 的区别

日志 115200 不等于烧录速度。当前烧录可使用 CH343 的更高波特率（先验证 921600）并只更新 app，不必每次更新 LittleFS。烧录完成后应用日志仍按固件的 115200 输出。

按存档原理图，H5 的 USB_DBG D+/D- 连接 CH343，H1 连接 P4 专用 HS DP/DM。内置 USB-JTAG 的 GPIO24/25 经 R72/R70 引到 USB1P1_N/P 信号，与 H1 的 USBD_N/P 不同。因此不能仅把现有 Type-C 换口就认定内置 JTAG 可用，需要确认这两条 FS/JTAG 信号的实际接线或采用适当的外部 JTAG。

SDK 官方资料：`docs/en/api-guides/jtag-debugging/configure-builtin-jtag.rst` 指定 P4 D-=GPIO24、D+=GPIO25。JTAG + OpenOCD/GDB 能断点、读双核栈与内存，也可以写 Flash；它对本故障的主要价值是现场调试，实际刷写速度需实测，不自动等于比高速 UART 快。本轮未安装驱动、未配置 JTAG 或更改 eFuse。

## 0.4.9 的下一步诊断

`[OuseFault v2]` 新增 22 个寄存器的只读快照：L1/L2 缓存访问失败标志和地址/属性、AXI ICM addrhole/deadlock、SRAM/ECC 状态和记录、AHB 错误、CPU 总线超时及错误响应配置。读取发生在 SDK `panic_enable_cache()` 之前。没有写入寄存器、清除标志、关闭错误响应或开启新的中断；记录地址必须结合对应 raw 标志解释，历史标志可能早于本次故障。
