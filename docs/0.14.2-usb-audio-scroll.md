# 0.14.2 USB 播放与后台页滚动修复

## 已确认的问题

后台页原本用顶部概览 label 的 `lv_obj_is_visible()` 判断是否离页。LVGL 的可见判断包含 viewport 裁剪，因此向下滑动时概览滚出屏幕便会删除服务/活动卡片，内容高度收缩，滚动回顶。现在判断整个页面的可见性；设置真正暂停时仍同步回收动态卡片。拖动/惯性期间延后快照更新，活动结束改变内容高度时保持可见服务卡片的滚动锚点。实机比较松手后两次快照，底部 USB 服务及重启按钮的纵坐标一致。

电脑枚举音频和 WinMM 缓冲完成不能证明扬声器已收到 PCM。本轮在原来的 1 ms HS 等时间隔下复现：音量 100%、未静音、USB 音频任务运行，但从 OUT FIFO 读到的样本数始终为零。修正反馈和空包处理后单独复测仍为零，因此没有把那一版当作修复成功。

HS 描述符现在使用 `bInterval=1`（每个 125 us 微帧服务），FS 仍为 1 ms。固定版本 DWC2 为下一微帧奇偶安排 ISO OUT，原来的 HS `bInterval=4` 下可能一直错过主机的固定发送相位；IN 有不完整传输重试，OUT 没有对应恢复。改变 HS 服务间隔后，真机持续收到 OUT 包及非零 PCM。静默 IN 的填充量相应改为 HS 每次 2 样本、FS 每次 16 样本，避免八倍填充。

## 固定 TinyUSB 的局部构建补丁

依赖仍锁定 0.21.0~2 / esp_tinyusb 2.0.1~1，未编辑 managed 源码。`components/ouse_usb/patch_audio_driver.py` 在构建目录生成局部覆盖文件，CMake 仅替换音频 class 的编译源：

- FIFO_COUNT 方法在收到首个播放包之前先建立非零 nominal feedback，先完成参数准备再安排第一笔反馈。
- 合法空包及软件 FIFO 满不能中断后续 OUT 接收安排。
- 添加无分配的原子收包/字节诊断计数。

脚本对所有替换点要求恰好匹配一次，源文件改变则构建失败，避免静默套用到不同版本。未改分区、显示、字体、Wi-Fi 或 NCM 网络行为。

## 诊断接口

`Ouse.usb.get()` 新增 `speakerSamples`、`speakerNonzeroSamples`、`speakerPeak`。前两项分别累计原生 worker 从 USB OUT FIFO 实际取出的样本及其中非零样本；峰值为取出样本的启动以来最大绝对值。这是进入板级输出路径的数据，不能单独证明声学出声。计数为启动以来 uint32 累计值（自然回绕），峰值范围 0..32768；不保存原始 PCM、不执行 I/O。每批最多扫描 64 样本，无额外缓冲分配。

调试固件的只读 `DBG_USB` 还报告主机请求、运行/错误、音量/静音、FIFO 欠载/溢出、底层 OUT 收包与字节、当前 feedback。相关采样不是同一时刻的原子联合快照。USB 网络共享未开启，不修改电脑默认路由或音频设备选择。

C API 15，JS API 1，固件 0.14.2。

## 验证边界

针对实际补丁函数检查 HS/FS 首次 feedback、空包/非空包/满 FIFO 连续 rearm；检查真实 ELF 的 FS/HS 描述符和真实 QuickJS USB 查询绑定。实机验证包括双向音频、仅扬声器播放（microphone=0）、后台页松手后等待刷新仍保持位置。没有用“缓冲完成”替代声学路径验证：在设备麦克风录音中，测试音期间检测到 440 Hz 分量约 119–120，播放结束后约 0.55；这是扬声器到麦克风的声学回采证据，实际听感仍需用户试听。

保持 USB 网络共享关闭，没有长时间压力测试或物理热插拔循环。内部 RAM 余量仍紧，既有内存压力问题不在本轮宣称彻底解决。
