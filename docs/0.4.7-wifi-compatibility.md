# 0.4.7：对齐存档 P4→C6 Wi-Fi 初始化

## 已确认的日志与差异

用户日志中 SDIO 已识别 ESP32-C6，卡初始化成功，收到了 INIT 事件并建立 TRANSPORT_TX_ACTIVE。失败发生在 `Req_GetCoprocessorFwVersion`，请求号 `0x15e`，超时后产品代码直接返回 ESP_FAIL；尚未运行到 `esp_wifi_init`。

已对照用户验证过的存档：

- `legacy/ESP32-P4-WIFI6-Touch-LCD-3.5/examples/esp-idf/04_wifistation/main/station_example_main.c`
- 同目录 `idf_component.yml`、`sdkconfig.defaults` 和 README_ZH.md。

示例初始化网络接口和默认事件循环、创建 STA 接口，然后运行 `WIFI_INIT_CONFIG_DEFAULT` / `esp_wifi_init`、设置 STA 配置、`esp_wifi_start`，通过事件连接并取得 IP。没有先查询协处理器固件版本。

存档在 IDF >=6.0 时选择 Hosted >=2.12,<3 和 Wi-Fi Remote >=1.6,<2；当前锁定的 Hosted 2.12.3、Wi-Fi Remote 1.6.5 属于同一范围，没有为本修复更改依赖或 SDK。

## 修复

移除首次初始化、传输恢复时强制调用的 `esp_hosted_get_coprocessor_fwversion`。继续在专属工作任务中启动 Hosted，保留延后初始化方式，随后按标准 Station API 判断实际能力；不恢复上游启动前的自动构造函数。

`esp_wifi_init`、存储/模式设置、启动、扫描和连接仍检查真实结果。初始化失败日志现在明确指出失败阶段，不会因为跳过版本查询就把初始化错误当成成功。

上游版本警告保留。其打印 Host 2.12.0 是比较时主动屏蔽 patch 位造成的，**不代表工程由 2.12.3 降级到 2.12.0**。Co-proc 0.0.0 可能是旧固件未上报版本信息，不能凭这一行认定真实版本为零，也不能据此保证协议完全兼容。

## 已完成验证

- 通过 COM10 在实际运行的 0.4.6 板子上安装 `user.usb-counter`，OPEN 指令成功；LIST 返回该 ID。
- USB 首次存储初始化后 HELLO 返回 `storage=ready`。
- 主机驱动测试模拟版本查询永远超时，确认首次初始化和传输恢复均不再调用它。
- 模拟真正 `esp_wifi_init` 超时，确认仍保持未就绪状态、报告失败、允许重试，不启动扫描。
- 保留已有无 C6、扫描去重、认证失败、IP/密码持久化、超时/恢复、关闭和忘记网络测试。

USB 的 OPEN 成功表示运行时接受启动；屏幕显示和重启后的应用恢复仍由用户验收。本修复未向板子烧录固件，Wi-Fi 扫描/连接是否成功需烧录 0.4.7 后确认。如果后续真正的 Wi-Fi RPC 仍超时，再根据具体调用、存档可用版本与 C6 固件信息处理协议兼容性。

## 烧录

同分区布局下，优先烧录 `tmp/ouse_core_desktop.bin` 到 **0x10000**，保留当前设置和已安装应用。完整合并镜像是 `tmp/ouse-core-0.4.7-full.bin`，地址 **0x0**，会重置 NVS 设置，保留 LittleFS。

烧录后应看到 `C6 Wi-Fi STA initialized through esp_wifi_remote`；随后观察扫描列表、连接及 IP。如果出现新的失败，请保留该日志阶段，不要只隐藏 Hosted 警告。
