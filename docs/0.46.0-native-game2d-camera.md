# 0.46.0：固件游戏计算与相机、相册

Core 0.46.0，Native API 48，JS API 1。BPK 继续携带 JS 规则与资源，新增的计算模块是固件中的 C++，不要求游戏改成 ELF。

## 固件游戏接口

`Ouse.game2d.version === 1`；`stepProjectiles(shots, targets, hits, dt)` 一次完成批量移动、寿命更新与圆形目标的连续弹道碰撞。配合已有原生 Canvas、精灵动画和音频构成混合实现；这次没有把整个游戏规则或渲染器重新实现一遍。

参数为三个互不重叠的普通 ArrayBuffer 和秒数。使用 Float64Array / Uint32Array 创建并复用缓冲，传入它们的 `.buffer`，避免逐实体跨语言调用及临时对象。

| 缓冲 | 每项内容 | 上限 |
| --- | --- | --- |
| shots，8 个 Float64 | x、y、vx、vy、life、radius、enabled（0/1）、excludedMask（无符号 32 位整数） | 128 |
| targets，4 个 Float64 | x、y、radius、enabled（0/1） | 32 |
| hits，Uint32 | 每个弹道对应的目标位掩码 | 与弹道数相等 |

`dt` 范围 0～0.125 秒；缓冲长度、有限数值、坐标/速度/寿命（绝对值不超过 1,000,000）、半径及掩码先整体校验，拒绝时不修改输出。不接受共享缓冲；内核用 memcpy 访问字节缓冲，支持 P4 JS 分配器的 4 字节对齐。每次调用无堆分配、无设备资源操作。碰撞保持原 JS 的严格相交及目标索引顺序，不按最近命中距离排序。

荒野生存 2.1.0 将 32 个弹道和 24 个敌人的批量计算接入此接口；伤害、穿透、爆炸、升级、AI 与关卡仍在 JS 中。没有接口的浏览器测试环境保留 JS 路径。已有 BPK 不需要改用 C++；要使用新接口，声明 `minNativeApi: 48`。

## 拍照与相册

- 取帧短暂超时最多尝试四次，中间等待 20ms；只重试取帧，不重试文件写入。继续使用临时文件、同步及重命名提交照片。
- 实机进一步复现 SD 单扇区写入返回 `ESP_ERR_INVALID_CRC`、卡仍在编程状态（R1 `0xe00`）。板级层等待 CMD13 确认 transfer/ready，再读回该扇区；只有 512 字节与原写入数据完全相同才确认成功。等待有界，内存不足、状态/读回失败或内容不同均保留原错误，不重放写入、不格式化。初次失败证据为 `.tools/game2d-device-sd-failure.log`。
- 取帧、编码、保存错误分别标记，界面不再把所有失败都指向 SD 卡。
- 相册保留当前页最多 12 个缩略图槽位；另一页的备用槽位接收新图，完成后返回稳定的 `entries[].image`。重叠图片保持槽位，不清黑当前页面。缩略图缓存上限为 24 张，客户端和 UI 两侧合计比原来多约 576 KiB PSRAM。
- 加载期间保留可见卡片样式，操作处理器仍阻止重复打开；滚动完成后保留加载期间的位移，避免透明度跳变和位置回跳。
- 相机预览保持传感器比例并显示完整画面；控件叠加在下方（竖屏）或右侧（横屏）。不同宽高比允许黑边，照片仍保存传感器完整画面。

相机/相册 BPK 升级至 1.2.0。API 48 的相册必须使用返回的 `entries[].image`，不能假设第 i 张恒为 `@thumbi`。固件更新后应同时更新这两个包。

## 整理

拍照事务和相册枚举/缓存分别移至 `ouse_camera_capture.inc`、`ouse_camera_gallery.inc`，主文件保留生命周期和工作线程。移除旧相机横排布局的对称占位控件；更新 README、STATUS 的当前版本入口，历史验证记录继续保留。用户已有的硬件设计、浏览器实验和未跟踪文件不在本次清理范围。

## 2026-10-26 设备验收

COM10 已更新最终 0.46.0 应用分区（`0x10000`），esptool 写入哈希验证通过，`DBG_BUILD` 与构建 ELF 的完整 SHA256 相同；没有重写 bootloader、分区表或数据分区。相机/相册 1.2.0、荒野生存 2.1.0 已同步安装。

最终启动后的首次、第二次按快门都成功：照片分别为 45,683 / 47,706 字节，CRC32 为 `ef55f81b` / `83851764`。设备此时尚未联网校时，试拍文件名为 `IMG_46_76dd9dc2_0001.jpg`、`IMG_48_76dd9dc2_0002.jpg`；检查枚举所有分页，不依赖未校时时间戳的排序。保留两张试拍照片及截图作为证据。此处是 RTS/EN 启动验收，不是断电冷启动或长期稳定性测试。

已查看竖屏底部控件、横屏右侧控件和相册截图；相册打开/滚动无脚本错误。结束相机/相册检查并释放其图像缓存后，荒野生存进入实际战斗，UART 报告 `SURVIVOR_ENGINE native` 和 `mode: playing`。另一次同固件场景截图显示约 23 FPS；未做相同场景的旧版对照，不宣称这就是性能增幅。随后追加了保留相机、相册后台上下文再启动游戏的检查：三应用共存时正常进入战斗，`contexts=3, errors=0`，记录在 `.tools/game2d-multi-app.log` 和结果目录的 `multi-app.json`。

最终 `errors=0`、`DBG_CHECK=ok=1`；临时测试包已卸载，原 34 个注册入口保留，恢复竖屏桌面，`live=0`，串口已释放。结果、照片 CRC、BIN/ELF/BPK SHA256 和设备串口记录路径保存在 `.tools/game2d-camera-device-check/result.json`，截图位于同目录，最终完整测试日志为 `.tools/game2d-device.log`。

## 后续性能配对测试与不限帧版本

同日追加了完整三轮 JS/C++ 实机动态回放，详见 [实机性能报告](survivor-device-benchmark.md)。不限帧中位数：8 敌人/8 子弹从 18.27 到 19.14 FPS；24 敌人/32 子弹从 8.38 到 11.05 FPS，后者模拟耗时从 41.33 降至 14.36 ms/步。测试限定每帧一个模拟步，并非所有实际战局的帧率保证。

正式游戏 2.1.1 解除原 25 FPS 人为上限，仍使用系统帧回调调度；该调整只更新 BPK，固件保持同一份 0.46.0 二进制。后续测试的累计错误计数及验证口径见性能报告，不能把本节前一次验收的 `errors=0` 当作所有后续调试期间的累计状态。
