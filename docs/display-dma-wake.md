# DMA 完成唤醒实验

本轮前的本地工作区存档为 `61337c5`。本轮仅改显示等待，不调整 SPI 时钟、刷新周期、40 行双缓冲或动画参数。

此前 UI 在 `display->flushing` 为真时每隔一个 RTOS tick 检查一次。当前 1000 Hz 配置下，该检查间隔为 1 ms。新实现使用一个显示专用二值信号量，在实际 `lv_display_flush_ready()` 完成后发出通知；ISR 使用 `xSemaphoreGiveFromISR` 并按需让出 CPU，任务内同步完成使用普通 give。不占用 adapter 的任务通知槽，不更改 managed component。

通过板级链接包装接入完成函数。最终 ELF 反汇编已确认 `display_manager_flush_ready` 跳转到包装函数。UI 被唤醒后仍检查 LVGL flushing 标志：残留通知或提前唤醒不能导致缓冲被提前重用；检查后、阻塞前发生的完成会留下信号量通知，不会丢失唤醒。初始化失败保留原有安全轮询。信号量与显示同寿命，启动时分配一次。

验证：

- `tools/test-display-flush-wake.py` 编译实际生产唤醒源码，以确定性 RTOS 替身覆盖 ISR/任务完成、阻塞前完成、残留通知、提前唤醒、分配失败回退和其他显示不串扰。
- `tools/test-ouse-core.py` 完整真实 LVGL 回归通过；异步单/双缓冲测试继续验证 DMA 完成前源缓冲不变。该测试模拟完成事件，不等于实机调度测量。
- ESP-IDF 固件构建通过；构建与 UI 日志为 `.tools/dma-wake-build.log`、`.tools/dma-wake-ui.log`。

本改动减少潜在的块间等待，不提供面板 TE 同步，也不保证消除撕裂。需以同样翻页动作进行真机对比，不能用绘制阶段统计冒充屏幕 FPS。

## 2026-10-19 真机验证

通过已授权 SSH 连接家里电脑，设备为 COM5 / CH343 `5CF7043459`。仅写入应用区 `0x10000`，esptool 写入哈希验证通过。BIN 为 6,681,200 字节，SHA256 `15751ffdff7216117430d8596144c6b003947cc7fa59ec02a3bec54d6e0d6553`。重启日志的 ELF 指纹匹配新构建。

旧、新固件各进行 32 次桌面翻页，两者堆完整性均 `ok=1`；新固件无 panic、意外重启或卡死。31 个 BPK ID、深色主题、中文、100% 字号和三键导航保持一致，最终在桌面，串口已关闭且无残留触摸。

短时日志筛选每 5 秒至少 100 次绘制且平均提交像素数据至少 200,000 字节/次的活跃大面积更新窗口，以绘制次数加权：旧固件 3 个窗口绘制阶段均值约 32.63 ms，新固件 5 个窗口约 30.07 ms；flush 等待平均每次绘制约 7.59 → 5.25 ms。启动/低更新量窗口不纳入此比较。该阶段包含等待且最后一块 DMA 可能未结束，采样也未严格隔离背景负载，因此只作为短时方向性证据，不表示面板 FPS，不证明肉眼撕裂已消失。

证据：`.tools/diagnostics/dma-wake-20261019/` 中的 `before.json`、`after.json`、原始 UART、烧录日志与 `after-transport.json`。
