# Core 0.40.0 / Native API 42：Canvas 绘制节点

固件增加通用 `canvas` 节点。一个节点对应一个 LVGL 对象，内部重放由 JS 提交的绘制指令，不为每个图元创建控件。精灵、图层、地图、碰撞和游戏逻辑可由 JS 库构建。现有 `sprite`、普通控件及 API 保持可用。

## 页面与接口

```json
{
  "api": 1,
  "units": "dp",
  "root": {
    "type": "canvas",
    "id": "world",
    "width": "fill",
    "height": "fill",
    "style": { "backgroundColor": "#182020" }
  }
}
```

App 清单声明 `minNativeApi: 42`。Canvas 可使用普通节点的布局、显隐、启用、字体与样式接口；不接受 `children`，每页最多两个 Canvas。通过 `Ouse.ui.on('world', 'pointerdown', handler)` 等现有指针事件接收输入，事件坐标沿用页面单位和节点局部坐标约定。点击事件也可注册。

原生入口为 `Ouse.canvas.submit(id, commands)`。一次提交完整替换该节点上一帧的指令列表，最多 256 条，空数组清空。提交返回只表示帧已接收，不代表已经显示。待显示帧尚未消费时，新帧覆盖待显示帧，队列不会积压。

```js
Ouse.canvas.submit('world', [
  { op: 'fillRect', x: 8, y: 8, width: 40, height: 20,
    radius: 4, color: 0xff8040 },
  { op: 'drawImage', src: 'actors', x: 80, y: 60,
    width: 16, height: 16,
    sourceX: 16, sourceY: 0, sourceWidth: 16, sourceHeight: 16 },
  { op: 'drawText', text: 'HP 100', x: 8, y: 40,
    width: 120, height: 24, color: 0xffffff }
]);
```

| op | 额外字段 | 行为 |
|---|---|---|
| `fillRect` | `width`, `height`, `radius` | 填充矩形，可圆角 |
| `strokeRect` | `width`, `height`, `radius`, `lineWidth` | 内边框矩形 |
| `drawLine` | `x2`, `y2`, `lineWidth` | 起点为 `x,y` |
| `drawArc` | `radius`, `startAngle`, `endAngle`, `lineWidth` | 圆心为 `x,y`；角度 0～360，0 朝右、顺时针；0～360 为整圆 |
| `drawImage` | `src`, `width`, `height`, `sourceX`, `sourceY`, `sourceWidth`, `sourceHeight` | 包内图像资源，裁剪后缩放到目标矩形 |
| `drawText` | `text`, `width`, `height` | 使用 Canvas 节点字体，裁剪到目标矩形 |
| `fillTriangle` | `x2`, `y2`, `x3`, `y3` | 填充三个顶点组成的三角形 |

所有指令支持 `opacity: 0..255`（默认 255）；图形和文字支持数值 `color: 0xRRGGBB`（默认白色）。坐标是整数，范围 ±16384，尺寸 1～4096，线宽 1～128，圆角/半径最多 2048。位置默认为 0，矩形尺寸默认为 1；实际使用应明确提供尺寸。文字最多 128 个 UTF-8 字节。图片源坐标/尺寸使用资源像素，目标坐标/尺寸使用页面单位；省略源矩形时使用整张图片。图片限包内资源，不接受 `@camera` 等原生服务图像 ID。首版不提供旋转、任意变换、路径或像素读回。

`tools/app-shared/canvas.js` 提供便利封装，打包时放在 App 脚本前面：

```js
const canvas = createCanvas('world');
canvas.beginFrame();
canvas.fillRect({ x: 0, y: 0, width: 100, height: 100, color: 0x182020 });
canvas.drawImage({ src: 'hero', x: 20, y: 30, width: 16, height: 16 });
canvas.endFrame(); // 只在这里跨入原生一次
```

调用顺序就是绘制顺序，后面的图元覆盖前面的图元。`beginFrame` 开始收集新帧，`clear` 提交空列表。App 暂停时停止自身游戏定时器；页面切换、关闭时由固件回收 Canvas 帧数据。

## 原生实现

- Worker 在锁外解析、复制所有参数并验证图片引用；通过后在模型锁内发布完整帧。非法提交保留原帧，JS 后续修改原数组不影响已提交数据。
- 帧缓冲按实际指令数在 PSRAM 分配。每节点只保留最新待消费帧和 UI 绘制帧，解析期间临时有一份新帧。每帧内存为 `sizeof(canvas_frame_t) + count * sizeof(canvas_command_t)`，已纳入 `nativeKnownBytes`。PSRAM 分配失败抛出异常。
- UI pump 在锁内切换不可变帧，锁外释放旧帧。绘制回调不持有模型锁，不调用 JS。
- 相同数量的指令按索引比较，合并变化前后包围框并标记脏区；完全相同的列表不触发重绘，增删指令或超过 32 条指令变化时整画布重绘，避免耗尽 LVGL 脏区槽位而退化成整块物理屏幕刷新。绘制时按脏区重放所有相关指令，正确恢复背景和透明叠加。
- 继续使用 LVGL 的软件绘制、现有显示缓冲和屏幕刷新链路，无额外全屏像素缓冲。图片裁剪和文字裁剪使用 LVGL 9.5 的内部 layer clip，相关依赖隔离在 `ouse_canvas_draw.inc`，升级 LVGL 必须重跑像素测试。

## 对照测试与复现

`benchmark-canvas` 和 `benchmark-json` 共用 `tools/app-shared/render-benchmark.js` 的运动公式、实体顺序、4 帧透明图集以及每帧图集索引。实体数为 8、32、64、96。JSON 版预建精灵、分批调用现有 `Ouse.sprites.update`；Canvas 版每帧批量提交图片指令。两边均不在游戏循环中创建 LVGL 对象。

```powershell
python tools/generate-render-benchmark.py
python tools/test-ouse-app-packages.py --apps benchmark-canvas benchmark-json
python tools/test-canvas-runtime.py
python tools/test-platform-runtime.py
node tools/test-render-benchmark.cjs
```

主机测试使用真实 QuickJS、生产 Canvas 绑定/绘制、生产精灵更新/动画逻辑及真实 LVGL 软件光栅化。测试夹具按固件方式构造 LVGL 对象，位置应用使用对应的 `lv_obj_set_pos`；不包含完整固件 UI pump、跨线程调度、PSRAM 时延或 SPI 传输。分辨率为 480×222、RGB565、480×32 行局部缓冲，flush 将像素复制到主机内存。

每组预热 40 帧，3 轮，每轮记录 160 帧，并交替执行顺序。统计场景准备、JS 提交、UI 同步、`lv_refr_now` 绘制至同步内存 flush，以及总时间的均值/P50/P95。自然脏区和强制全场景刷新分别测试。96 个独立场景帧逐像素比较；全部 4800 对连续帧在计时区外比较 64 位像素哈希。另测所有图元、透明、图集裁剪/缩放、画布边界、dp 缩放、非法参数原子拒绝、帧替换及重复清理。

原始逐帧记录、汇总和截图输出在 `.tools/canvas-runtime-check/`；本次汇总保存于 [canvas-host-results.json](canvas-host-results.json)。这是主机 CPU 成本对比，不能换算成实机 FPS。

## 本次主机结果

| 实体数 | JSON 精灵总耗时 | Canvas 总耗时 | JSON / Canvas |
|---|---:|---:|---:|
| 8 | 0.062 ms | 0.042 ms | 1.48 倍 |
| 32 | 0.279 ms | 0.156 ms | 1.79 倍 |
| 64 | 0.674 ms | 0.189 ms | 3.56 倍 |
| 96 | 1.196 ms | 0.276 ms | 4.33 倍 |

表中为自然脏区、场景准备＋提交＋UI 同步＋绘制到主机内存的平均总时间。8 个实体两边平均刷新约 2498 像素；32 个实体 Canvas 约 9873 像素、JSON 精灵 106560 像素；64/96 个实体均约 106560 像素。完整汇总同时提供强制全场景刷新数据，以区分脏区策略与对象管理成本。

Canvas 的 JS 提交更贵，收益主要来自 UI 同步和场景绘制。32 个实体时局部刷新有更多分块，主机绘制阶段反而比强制全刷新更慢，但发送像素少；真机收益需结合 SPI 和 DMA 测量。不得由该表宣称实机同等倍率或达到某个 FPS。

## 本次真机结果

COM10 开发板，Core 0.40.0 / Native API 42；物理屏幕 480×320，游戏场景 480×222。两种实现均使用 50 ms 定时目标，共享实体运动公式和图集，每档 200 次更新，四档全部完成后自行停止。结果为一轮实机观测，不是最大吞吐量测试，也不代表显示面板的独立扫描帧率。

| 实体数 | JSON 场景更新/秒 | Canvas 场景更新/秒 | Canvas / JSON | JSON 绘制阶段均值 | Canvas 绘制阶段均值 |
|---|---:|---:|---:|---:|---:|
| 8 | 15.02 | 14.78 | 0.98 倍 | 3.91 ms | 3.04 ms |
| 32 | 9.76 | 16.81 | 1.72 倍 | 34.25 ms | 11.75 ms |
| 64 | 5.96 | 16.77 | 2.81 倍 | 34.35 ms | 22.83 ms |
| 96 | 4.21 | 15.13 | 3.59 倍 | 34.36 ms | 23.28 ms |

场景更新率使用 `BENCH_STAGE` 至 `BENCH_SUBMIT` 的设备单调时间和实际 200 次更新计算，包含脚本、锁等待及系统调度影响。绘制阶段来自完整落在同档位内的 5 秒 `OuseDisplay` 统计窗口；跨档窗口已排除。当前驱动的绘制阶段包含 flush 等待，不能再把 flush wait 加上去。脚本 Date.now 统计为毫秒粒度，最大值也受诊断截图/调度影响。

8 个实体差异很小；密集场景的主要收益来自减少控件更新、遍历及屏幕传输。96 个实体时，JS 准备/提交均值为 JSON 58.82 ms、Canvas 22.18 ms；每次刷新平均发送约 JSON 304239 字节、Canvas 214579 字节。Canvas 的改善不只来自绘制函数本身。测试场景只有运动和图集动画，没有碰撞、寻路或实际游戏战斗逻辑。

最终两套应用关闭后均为 `instances=0, contexts=0, widgets=0, timers=0, errors=0`，heap `ok=1`；捕获中无 panic、无意外重启，串口已关闭。已恢复测试前的横屏天气页面，恢复后 errors 仍为 0。两个测试应用保留安装，打开即可重新运行。
