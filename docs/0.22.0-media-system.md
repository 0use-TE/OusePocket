# Core 0.22.0: gallery, notifications, recorder and HTTPS

Native API 25; BPK/JavaScript API remains 1. Camera remains photo-only.

## Gallery

- The grid has an Album heading; the full-screen viewer does not.
- A fixed twelve-thumbnail window shifts by one row while scrolling. Matching
  native PSRAM thumbnails are reused, not decoded again on every shift. The
  viewport is repositioned by the removed/inserted row height. Reverse scrolling
  loads the preceding row; stationary scrolling does not oscillate between windows.
- Metadata scans remain bounded by the existing 4,096-offset native API and
  three-second scan deadline. This is not an unbounded recursive photo index.
- Viewer deletion requires confirmation. Native `Ouse.photos.remove(path)`
  stops playback and removes only a supported JPEG/AVI directly in SD
  `Ouse/Pictures`. It cannot delete arbitrary SD paths or internal storage.
- Capture dates come from the timestamp in system-created IMG/VID filenames.
  Missing/invalid timestamps display as unknown, not as a fabricated capture
  date from a copied file's modification time. External EXIF parsing is not added.
- Native MJPEG AVI playback/replay remains available; arbitrary MP4/H.264
  playback is not introduced by this change.

## System chrome

The right status area has three Wi-Fi signal levels and a disconnected symbol.
Cached RSSI is refreshed by the existing board Wi-Fi worker. New notifications
slide down below the status bar and disappear after 4.5 seconds. The banner
opens the notification owner's app and can be dismissed. A status dot remains
until the notification center is viewed. Updating an existing ongoing music
notification does not repeatedly trigger banners. Notifications do not wake a
sleeping display; recents, sheets and modal dialogs suppress the banner.

## Music ownership

Home and switching apps continue playback. Explicit close, clearing recents,
uninstall and script faults cancel the native media session by exact instance
owner. Codec/producer cleanup remains asynchronous and acknowledged before
task completion. Delayed cleanup of an older instance cannot stop a newly
opened instance with the same application ID.

## SD recorder

`user.recorder` requires `files` and `media` capabilities. `Ouse.recorder`
provides `get()`, `start()`, `stop()`, `list(offset)`, `rename(path,name)` and
`remove(path)`. Start/list/rename/remove return task IDs or false; stop requests
cooperative finalization. Paths are restricted to SD `Ouse/Recordings/*.wav`.

The existing single codec worker owns microphone/I2S access. Recording rejects
another active audio owner rather than silently stealing the microphone. A
64-KiB PSRAM stream separates PCM acquisition from SD writes. WAV format is
PCM16 mono 16 kHz. Writes are bounded; overflow, missing SD, write errors and
empty recordings fail rather than publishing an invalid final file. File
headers, fsync, close and rename finish before publishing a successful result.
The restart coordinator also waits for the recorder writer to become idle.

The UI offers start/stop, elapsed time, a twelve-item recording list, playback,
rename and confirmed deletion. Stop saves a unique default filename first,
then asks for a name; keeping/cancelling naming does not discard the recording.
Closing or backgrounding the app stops acquisition and finalizes the default
file. Rename preserves its modification time, used as recording end time.
Without synchronized wall time, the UI honestly reports an unknown end time.
Internal Flash is never used as a recording fallback. The initial native
recording limit is approximately one hour; this is not a long-duration soak
test claim.

## HTTPS

The HTTP service retains CA-bundle, hostname and validity verification. Enable
`CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_CROSS_SIGNED_VERIFY` in the product config:
the physical Baidu test reproduced a chain ending in a cross-signed GlobalSign
R3 certificate, whose issuer was not in the default current-root bundle. The
SDK's supported cross-signed-root lookup fixes this without trusting a peer's
arbitrary root, disabling hostname checks or accepting expired certificates.

Device network tests require working Wi-Fi and synchronized time. A failure
while disconnected is not evidence that HTTPS/TLS is unsupported.
An existing locally retained `sdkconfig` must also enable the cross-signed
option explicitly; product defaults alone do not override a saved `n` value.

## Validation

- Production BPK parser/schema and QuickJS compilation: camera, gallery, music,
  recorder.
- Camera/gallery and recorder JavaScript interaction regressions.
- Real board codec worker: PCM format, exclusive busy rejection, cleanup order,
  startup error propagation, existing audio and alarm/media-focus regressions.
- Real recorder finalizer on a disposable host filesystem: WAV header/payload,
  cancellation retention, absent card/empty failure, no overwrite, scoped paths.
- HTTP framing/TLS configuration and media instance-owner cancellation tests;
  SD file-service, camera-driver and Hosted-memory regressions.
- Physical tests: notification banner lifetime; recording save, naming/list,
  rename, playback and confirmed deletion; closing during recording; music
  survives Home but stops on explicit close; synthetic photo/video direct
  preview, timestamp, replay and confirmed deletion. Test media is synthetic;
  existing user photos/videos are not downloaded or deleted.

Final physical HTTPS checks returned HTTP 200 for Baidu robots.txt (2,814 bytes)
and favicon.ico (16,958 bytes). Accessing the same service by its IP rather than
its certificate hostname failed certificate verification (`-0x2700`), as it
should. No certificate checks were disabled. A final banner lifetime check also
passed. With test apps closed, runtime reported zero contexts/script errors,
heap integrity `ok=1`, internal free 77,216 bytes, minimum 37,664 bytes after TLS.
Final continuous-scroll up/down checks also passed. The temporary HTTPS probe
was uninstalled; the existing application set is retained with Recorder added.
