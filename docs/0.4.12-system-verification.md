## Wi-Fi：六条失败前与修复后证据

`tools/test-ouse-wifi.py` 编译产品实际 `board_wifi.c` 与 `ouse_devices.c`，通过状态型 SDK/事件替身驱动真实 worker。替身模拟初始化、物理 started 状态、实际关联状态及可控失败；每个新增用例在独立进程运行，避免静态状态串扰。这里验证的是实际 worker 的状态处理，不是执行真实无线连接。

| 缺陷与触发 | 失败前证据 | 修复后行为 |
| --- | --- | --- |
| 断开后重新拿 IP，两事件在 worker 唤醒前合并 | 固定先处理 IP 再处理断开，最后 `connected=0,connecting=1`，connect 次数 2，而预期 1 | 在事件锁内保留最后一次连接状态通知；先断开后 IP 保持连接且不多连，反向顺序拒绝旧 IP；transport DOWN 仍优先 |
| `esp_wifi_stop` 失败后再次关闭 / 再开启 | worker 无条件将 started 清零；再次关闭没有真正 stop，累计 stop 仅 1 次、物理仍开而 worker 认为已关 | 只有 stop 成功或明确 NOT_STARTED 才清 started；失败可再次关闭，也可在仍运行的驱动上重新启用，不重复 start |
| 自动重连调用立即失败 | error 已为 ESP_FAIL，但 `completed_id=0,request_id=2`，请求没有完成标记 | begin_connection 失败立即完成当前请求；后续显式连接仍可成功 |
| 初始化配置失败且 deinit 也失败 | 丢掉已经分配的驱动状态，再次 init，测试返回 INVALID_STATE；init 累计 2 次、ready=false | 单独记录驱动已创建状态；清理失败保留该状态，在原实例上重试配置；成功后 ready=true，init 保持 1 次 |
| 已连接状态收到新的 DHCP IP | worker 只接受 connecting 状态的 GOT_IP，仍显示 192.168.1.7 而新地址为 .8 | connecting 或 connected 均验证实际 AP 后刷新 IP；同一连接的地址变化不重复初始化 SNTP |
| Office → Guest 后，Office 的迟到断开/认证失败事件 | 旧事件终止 Guest 请求，`connecting=0,error=ESP_FAIL`；也可能覆盖 Guest 已排队的 IP 通知 | 事件锁保护当前请求 SSID；带有其他 SSID 的迟到断开在合并前被忽略，Guest 继续连接；SSID 缺省事件仍兼容 |

失败前原始主机日志保留：

- `../.tools/verification-0411-wifi-state-before.log`：前四条失败；原有基线、SNTP 重试及初始化请求抢占原本通过。
- `../.tools/verification-0411-wifi-events-before.log`：首轮修复后补充定位，DHCP 地址更新与旧 SSID 事件仍失败。
- `../.tools/verification-0411-wifi-state-after.log`：六条修复后，原有基线与下列 11 个独立用例全部通过。

上述日志名称保留创建时的 0411 前缀；这些新源代码修复归属 **0.4.12**，不是补记 0.4.11 硬件通过。

| 新增用例 | 已验证的主机路径 |
| --- | --- |
| `merged-events` | 断开→IP、IP→断开的两种顺序；认证失败→IP 的最后状态 |
| `stop-retry` | stop 失败后再次关闭实际调用 stop，随后可以正常再开 |
| `stop-reenable` | stop 失败后直接再启用，不重复启动仍运行的驱动 |
| `reconnect-failure` | 自动重连立即失败有完成标记，显式重试恢复 |
| `init-cleanup-retry` | mode 配置失败、deinit 失败后重试，不重复分配驱动 |
| `sntp-retry` | SNTP init 失败不破坏 Wi-Fi 连接，下一次 IP 重试，成功后不重复 init |
| `dhcp-ip-change` | 已连接后 .7→.8 地址刷新，以及合并断开→.9；不额外 connect/SNTP init |
| `superseded-disconnect` | 切换 SSID 后旧认证失败被忽略；旧事件不擦掉新请求的排队 IP |
| `untagged-disconnect` | 未附 SSID 的断开事件仍触发当前连接的正常重试 |
| `transport-before-ip` | 同批 transport DOWN 优先于 IP，不误保存凭据或启动 SNTP |
| `superseded-init` | 初始化期间出现更新的关闭请求，旧请求不再启动或扫描 |

原有基线仍覆盖默认关闭不启动 Hosted、C6 缺失、真正 Wi-Fi init 错误、扫描去重、认证失败不保存密码、连接后保存/IP/RSSI、有限重连、超时、transport 重试及 off/forget。

本机 SDK 源码确认 `ESP_NETIF_SNTP_DEFAULT_CONFIG` 的 `start=true`，初始化成功会启动 SNTP；失败路径释放内部 storage。当前代码只有成功后才设置 `sntp_started`，没有在 UI 线程等待校时，本次无需改 SNTP 实现。主机结果不能证明真实 DNS/NTP 网络连通或准确校时。

## 电脑串口控制：失败状态与收尾

`tools/device.py` 的电脑端串口所有者增加完整错误留存和独立资源收尾，`tools/test-device-transport.py` 通过假串口向实际 Device 类注入失败，18 项全部通过。测试不打开 COM 端口、不访问板子；log 中 `Guru Meditation Error: fixture only` 和 8 字节转储均为明确的测试数据，不是新增硬件 panic。

行为变化：

- 构造失败时关闭已经获得的资源；旧证据目录不覆盖。
- 读取线程已报错后，在写出新请求前拒绝操作；write/flush 失败记录首个错误与全部错误，不自动重连、不复位设备。
- 按下命令 ACK 未知时仍保留待释放接触；链路健康可补发 release，但最初超时仍为失败。I/O 已失败则停止 TX，保留未知接触供诊断。
- 每项资源分别关闭；close 再次失败不能盖掉原测试异常。先前的主机错误/超时不能被后续成功请求或正常 context exit 抹成通过，已验证的设备协议 ERR 则与主机传输故障区分。
- 已开始但尚未完整的转储按原捕获流程等待收尾；TX 失败而 RX 仍健康时继续接收，不发送新操作或复位。reader 仍未退出时不关闭其拥有的捕获句柄。
- `transport.json` 保存错误阶段/traceback、首个和全部错误、独立 cleanup errors、待释放/已确认接触、RX 状态及捕获终结状态。

证据为 `../.tools/device-transport-check.log`，该日志首行给出本轮每个测试原始字节和 `transport.json` 的独立证据根目录；完整列出 18 项名称。覆盖构造/开口/初始同步写失败、证据不覆盖、reader WinError、write/flush、丢按下 ACK 与 tap 释放、读资源后不能误发 FREE、串口关闭失败仍收尾其他句柄、原异常保留、已捕获 reader 错误不变成正常退出、协议拒绝分类，以及未完成转储/写失败后完整接收两种路径；另有正常 HELLO/资源 CRC/tap/swipe/close 基线及 DBG_IDLE ACK 丢失后的恢复义务检查。

这不是 Windows WinError 5 的根因修复，也不是板端总线异常修复。旧故障时间前后约 2 分钟的 Windows 日志没有可归因的 USB 事件，且 DriverFrameworks Operational 未开启，不能据此确定驱动、线缆或板子原因；原硬件长跑 failed 记录保持不变。本版真实串口/MCP 集成仍待验。
