# 显示滚动优化与应用打开动画分析

## 本次显示改动

- LVGL 默认刷新周期由 33 ms 改为 16 ms；触摸读取单独使用 8 ms。FT6336 中断仍决定是否读取 I²C，不把轮询频率称为触摸芯片实际采样率。
- UI 任务等待范围由 5～20 ms 改为 1～16 ms。LCD 忙时继续让出 CPU，只有实际 DMA 完成后才允许复用正在发送的缓冲。
- BSP 的单块 50 行绘制缓冲改为两块 40 行内部 DMA 缓冲。320×40×2×2 = 51,200 字节，比原有 32,000 字节增加 19,200 字节。使用 LVGL 的 PARTIAL 双绘制缓冲，让 CPU 绘制下一块时 SPI 可以发送上一块。
- 通过产品板级链接包装调整公开的 adapter profile，保持 BSP 的屏幕/触摸生命周期、缓冲分配和释放入口，不修改 managed_components。
- 状态栏时钟、电量、Wi-Fi/蓝牙图标和快捷面板的文字、颜色只在变化时更新。普通状态轮询只校正颜色，不再反复把状态栏移动到导航栏上方、再把导航栏移回来。主题/语言代次变化仍会重绘自绘图标。
- 调试构建每五秒输出一次 `OuseDisplay` 汇总：绘制阶段平均/最大时间、flush 等待时间、提交块数和字节数。无绘制时不输出。绘制阶段包含等待，最后一块 DMA 可能仍在进行；这些数值不是面板 FPS，也不是独立的 DMA 传输耗时。

## 硬件边界

归档板级原理图的 LCD 连接器 J12 没有引出 TE 信号；`TP_INT` 是触摸中断，不能拿来当显示同步信号。因此保留 SPI 的 `TEAR_AVOID_MODE_NONE`，没有启用一个未连接的 TE GPIO。

双绘制缓冲可以重叠绘制/发送，但不等于面板显存的同步换帧，不能保证消除扫描撕裂。单线 80 MHz SPI、320×480 RGB565 整屏像素传输理论下限为 30.72 ms，约 32.6 次/秒；命令、绘制和等待还会增加耗时。16 ms 是刷新调度周期，不是整屏稳定 60 FPS 的承诺。

## 应用打开动画：仅分析

当前 `components/ouse_core/ouse_core.c` 中 `launch_app()` 直接调用 `ouse_app_open()`。后者创建/恢复应用根节点，再立即切换前台。`ouse_shell.c` 的 `flight` 逻辑用于上滑离开应用，不是图标进入应用的动画；`ouse_boot.inc` 是开机动画。

用户记得的效果保存在 `legacy/components/brookesia_system_super/src/shell_launch.cpp`：

1. 从桌面被点击图标的边界开始显示遮罩和图标；没有起始位置时使用默认位置。
2. 背景的 x/y/宽/高展开到全屏，图标的 x/y/宽/高同时变到屏幕中央的 96×96。
3. 八个属性使用 220 ms ease-out 动画，完成后进入 `schedule_app_start_after_launch()`。
4. 默认额外停留为 0 ms，随后才调用 `activate_app()`，最后撤掉遮罩。

这段动画属于旧 Brookesia 框架，没有移植到当前原生 Ouse Core。它不是被某个当前开关关闭，也不是这次显示优化删除的。

如恢复效果，建议用原生 LVGL 的单个过渡进度统一计算背景和图标位置/尺寸，持续约 180～220 ms；避免八条重复布局更新、全屏实时模糊和每帧截图。可在动画期间并行推进现有异步加载，等首屏准备好再撤罩，不必照搬旧版“动画结束后才开始加载”的等待顺序。需要覆盖重复点击、返回取消、加载失败、包更新/卸载时图标资源寿命，以及从最近应用恢复的不同入口。本次没有加入或修改应用打开动画。
