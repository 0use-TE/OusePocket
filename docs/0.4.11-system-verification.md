# 0.4.11 系统验收与证据

0.4.11 保留默认显示 flush 等待修正，新增前台脚本关闭生命周期和卸载重试修复。首个本版构建发现的原生空白处滚动和音频 I2S 状态问题已修复；后续 `c3eb68692…` 构建的服务、BPK、系统/导航、1000 次重绘、MCP、独立追加 20 轮长跑和最后 3 次串口复位检查已完成。原 60 轮长跑在第 46 轮因 Windows 串口 I/O 错误中断，整次仍记失败；无复位重连后板端 uptime 连续、堆检查正常，串口中断原因未确定。本文区分每个 ELF 和每次运行的证据，避免把已完成子项当作全系统无失败通过。

## 已确认的故障路径

原默认异步 SPI 刷新等待使用 `while (disp->flushing);` 紧循环。同一个 `b262c5f5a7` 二进制中，仅启用让出 CPU 的等待回调，保留真实 LCD/Wi-Fi/WFI，板上 Unity 5 项和 30 轮混合操作通过，共发生 10238 次真实等待。重启后在同一二进制切回紧循环，通过 4 轮，第 5 轮发生 HP WDT 复位，RTC 首异常记录 Core1 调度器 BUS_ERR 和 Core0 中断 WDT。

另一个 `015a770ff2` 二进制在正常 LCD 传输时直接出现 Core1 对合法 SRAM/PSRAM 地址的总线异常，对端硬件 PC 位于 `wait_for_flushing`；同一二进制仅跳过实际 LCD 传输时通过 30 轮、11539 次 flush。后者是诊断对照，不能作为正常固件稳定性通过。PSRAM 降至 80MHz 仍失败，主配置保持 200MHz。

这些证据支持修正显示等待路径，尚未证明具体硅片仲裁 errata，也不能据此把故障归结为某个第三方组件、Wi-Fi 或整体架构。`CACHE_SYNC_CTRL=0x10` 表示同步已完成，不能解释成缓存同步尚未结束。V0.3 使用相同核心 SDK/LVGL/等待路径，用户先前正常体验不等于已经覆盖后来的并发负载。

默认实现通过官方 `lv_display_set_flush_wait_cb()`，每次 `vTaskDelay(1)`，直到原 LCD 完成中断清除真实 `flushing` 标志才返回；不提前 `flush_ready`、不复用仍由 DMA 使用的缓冲。固定 LVGL 私有 display 布局的兼容边界和完整现场见 [总线超时定位](0.4.10-bus-timeout.md)。主机真实 LVGL 检查模拟第 3 次让出后 DMA 完成，并验证等待期间缓冲未变；记录在 `../.tools/ouse-core-flush-wait-check.log`。

### 首次测试暴露的两项缺陷与修复证据

原生滚动：设置主页的 `(160,180)` 位于控件之间的空隙。真机连续 5 次由该点向 `(160,55)` 拖动，树与截图均未移动，证据在 `device-0411-native-scroll-repro/tree-0.json` 至 `tree-4.json`、`settings-0.jpg` 与 `settings-4.jpg`。`ouse_widget_box()` 默认移除 CLICKABLE，而设置列仅重新加入 SCROLLABLE，空隙触点落到外层而非滚动页。修复只为设置列、快捷内容区和 Wi-Fi 表单三个滚动容器重新加入 CLICKABLE。

同一真实 LVGL 指针回归在修复前显示 `scroll_y: 0→0` 并断言失败，修复后同坐标拖动为 `0→312`。补充回归确认起点不落任何子控件，PRESSED 的目标就是滚动容器；快捷内容空隙拖动为 `0→94`，Wi-Fi 表单在受限 120px 视口下为 `0→25`。测试使用真实 indev 输入，验证后才通过 API 恢复独立用例的布局。前后日志分别为 `../.tools/ouse-core-settings-gap-before.log` 和 `../.tools/ouse-core-settings-gap-after.log`；后者完整三场景及既有 200 轮生命周期通过。对应图片在 `../.tools/ouse-core-check/`：`settings-gap-scroll.png`、`quick-gap-scroll.png`、`wifi-form-gap-scroll.png`。

音频：首个构建硬件两轮中观察到 `playing→idle`、`recording` 时长 `192→832→1472→2112→2752→3000ms`，回放/停止后回到 idle；但反复出现 `E ... i2s_channel_disable(1516): the channel has not been enabled yet`。这说明命令状态结束并不等于驱动调用没有错误，也没有验证扬声器听感或麦克风声音质量。

主机状态审计在修复前记录 `invalid transitions=8, redundant format changes=2, configured DMA frames=0` 并失败。固定板级格式、查询通道实际状态后启停、TX 启动前填充静音、设置 256 帧 DMA，并将数据接口错误返回给 worker 后，审计变为 `0 / 0 / 256`，回归通过；还覆盖预填充/启动/停止失败、部分双工启动回滚、重试和清理顺序。证据为 `../.tools/verification-0411-audio-before.log` 与 `../.tools/verification-0411-audio-after.log`。这些是主机状态测试，不替代后续 ELF 的真实 I2S 日志与音频复验。

## 采样方式与失败判定

板上控制复用串口工作任务，只有收到显式命令才运行，不增加后台采样任务：

- `DBG_HEAP`：内部 8-bit 堆和 PSRAM 的 free/largest/minimum/total，以及任务数。
- `DBG_CHECK`：执行 `heap_caps_check_integrity_all(true)`。
- `DBG_REPAINT`：投递 UI 回调，仅使当前 screen 无效以触发重绘。
- `DBG_FLUSH status`、`DBG_LCD status`：确认正常等待启用、实际 LCD 开启且没有跳过传输。

调试命令依赖 `CONFIG_OUSE_DEVICE_DEBUG`。`DBG_FLUSH 0`、`DBG_LCD 0`、`DBG_IDLE 0` 只用于单变量对照，不能把关闭等待、关闭显示或跳过 WFI 的结果当作默认固件最终验收。

内存应在字体/JS/预览热身后、相同页面与实例数量下比较，关闭应用和动画完成后再取样；最低历史空闲值本来只降不升，不能单独据此认定泄漏。记录 free、largest、任务数和活动实例，排除当前仍持有的预览/包缓冲，再判断反复清理后的持续下降。

出现 panic、非预期复位、堆损坏、串口协议长期无响应、应用状态错误、关闭后资源持续累积，任何一项均记失败并保留现场。Windows 串口断开/拒绝访问单独记录，没有 MCU 证据不能直接称作板端崩溃。

每次实机记录保存原始串口、带时间的操作序列、结构化结果、固件版本/ELF SHA256、匹配 ELF/MAP/sdkconfig，以及必要的截图。失败时停止注入并收全转储，使用匹配文件解码，避免把重启后异常和首次异常混在一起。

### 60 轮长跑的串口中断与无复位恢复
