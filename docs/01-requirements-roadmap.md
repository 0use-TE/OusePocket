# 需求与分阶段路线

日期：2026-10-14。优先级是建议，不代表删除后期目标。总体产品定位：能离线使用的触摸工具机，通过 Wi-Fi 或手机伴侣扩展服务。实物已有摄像头、电池和 SD 卡；手机验收目标为三星 A56 / Android 16；USB 首版为 Windows；商店自用可信、无人工审核；云端为 Linux，后端优先 ASP.NET Core。

## 阶段与退出条件

### M0：硬件与框架路线验证

分别运行微雪的显示/触摸、SD、音频、Wi-Fi 示例，记录实物 revision、依赖版本和结果。测全屏刷新、音频缓冲、可用内部堆与 PSRAM。随后在独立试验工程验证新 Brookesia 的板级接入、320×480 桌面、真实背光设置以及一个动态应用包。

退出条件：明确选用哪套 Brookesia/ESP-IDF/LVGL/Hosted/BSP 版本，保存锁文件；实测记录与失败列表齐全。新路线失败时先定位板级、依赖或框架问题，再决定是否临时使用旧 Phone 路线。不能只凭“最新版”决定。

### M1：最小可日常使用系统

桌面 + 设置 + 文件 + WAV 音乐 + Wi-Fi + 日志诊断 + 整机 OTA。验收：连续使用一小时并重复切换应用，监测内存是否持续下降；重启后配置保留；缺卡/断网可操作；升级中断能重新启动。时间与性能指标是拟定验收目标，尚未实测。

### M2：媒体和 GPIO 工具

接入相机、相册、受限视频格式、串口工具、舵机工具与 USB CDC 转 TTL。先实现资源仲裁：相机与视频是否允许并发，串口被桥接时调试器如何提示，舵机退出时是否停止 PWM。每个应用都要有异常和退出路径。

### M3：Android 伴侣

独立 Android 伴侣应用承担通知监听、BLE 配对、文件/二维码导入。在三星 A56 / Android 16 上先完成小消息同步，再试云请求代理；通知可用不代表蓝牙联网可用。测试锁屏、手机应用被系统回收、权限撤销、离线和 Wi-Fi/BLE 并发；Google 服务可用不替代这些实测。

### M4：USB 音频/网络和云 AI

USB 模式先在 Windows 上单独实现，每次选一个模式；复合设备之后再评估。云端先做文本 AI，再做语音和工具。USB 网络、UAC、AI 都用后台任务，主界面保持响应。验收对象须记录 Windows 版本、格式、采样率、带宽和长时间运行条件。

### M5：动态应用与云端商店

如果 M0 采用新 Runtime，M5 是产品化完善；如果采用旧 Phone，必须先迁移或引入运行时。先发布一个只读信息应用，证明下载、安装、启动、更新、卸载闭环，再发布需要音频或 GPIO 的应用。应用商店后端从 HTTPS 目录清单和可信包存储起步，之后再做发布后台和账户。

商店按自用可信应用设计：由 Ouse 直接发布，不设计人工审核队列、第三方入驻或复杂运营后台。兼容检查、来源验证、更新恢复仍属于安装可靠性要求。后端优先 ASP.NET Core，部署 Linux；管理页可用 Blazor 或 Svelte。

## 范围边界

第一版不承诺通用 Android/Linux 应用兼容、任意 MP4 解码、微信/QQ 客户端登录、动态付款码复制、BLE 通用互联网共享或任意第三方原生插件安全隔离。

功能较多，不宜现在给出固定完工日期。依赖图可理解为：板级基线 → 服务 → 桌面/设置/内置应用 → 可恢复更新；手机与 USB 可以在稳定服务接口上独立扩展；动态商店依赖运行时和发布规则。
