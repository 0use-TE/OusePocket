# 自动复现：总线访问超时与显示等待修正

当前定位到可重复的显示等待触发路径：同一个二进制中，真实 LCD 传输保持开启，让出 CPU 等待完成通过 30 轮；切回原紧轮询后第 5 轮复位。默认修正已通过 COM10 烧录，使用 LVGL 的 flush-wait 回调等待原完成中断，每轮等待阻塞 UI 任务 1 tick，避免持续紧轮询。没有提前清除完成标志。

最终固件仍为 0.4.10，ELF SHA256 `33a838cbd9a270aa4dc5f00c435872d26cd5ba2d62bd1f3bdc7743a745c76a8a`。默认配置下真实板上 Unity、40+10 轮混合应用/手势测试和真实 MCP 集成通过；共 3 次启动（烧录后启动加两次串口硬复位），未再捕获总线异常或异常重启。最终状态确认 flush wait enabled=1、LCD enabled=1/skipped=0；COM10 已释放。Wi-Fi/SDIO、CPU 400 MHz、PSRAM 200 MHz、XiP 保持开启，NVS/LittleFS/BPK 未擦除。

这些对照支持当前显示等待修正，但没有证明芯片内部具体仲裁机制，也不代表已排除所有可能的稳定性问题。V0.3 使用相同等待路径、核心 SDK/LVGL/显示配置；版本增加负载和改变时序可能暴露潜在问题，不能据此要求整体架构重写。

最终证据：`.tools/diagnostics/device-0410-flush-default/`、`device-0410-flush-default-boot2/`、`mcp-0410-flush-default/`、`device-0410-flush-final-state/`。完整本地主机回归记录：`.tools/ouse-core-flush-wait-check.log`。

以下保留历次诊断，初始 200 MHz 构建的 ELF SHA256 为 `14ccb0925d85109ffea5cbec045b1f00ccb1c400171740e6f46d11f4de571884`。

## 现场区分

1. `.tools/diagnostics/device-0410-first/`：5 项板上 Unity、触摸计数、JPEG 和按住概览通过，之后 Windows 串口 GetOverlappedResult 拒绝访问，未记录 panic。重开串口可读到正常 0.4.10 状态。不能把这一次串口错误算作 MCU panic。
2. `.tools/diagnostics/device-0410-regression2/`：自动切换过程中先发生 `HP_SYS_HP_WDT_RESET`。重新启动到首个显示刷新附近再次异常，Core0 在 WDT 喂狗 ROM 例程读取内部 `init_context`，BUS_ERR=1、PMP_ERR=0。ICM raw=1、deadlock=0x31、core_timeout_raw=0x30。此转储捕获的是重启后异常，不能当成首次 WDT 前的瞬时状态。完整 319200 字节，通过官方加载器校验。
3. `.tools/diagnostics/device-0410-final/`：串口复位后启动时仍出现相似异常，完整转储已保留。随后用户完全断电再上电，MCP 控制接口恢复，实机 MCP 回归通过。
4. `.tools/diagnostics/device-0410-cold-regression/`：断电恢复后自动测试直接捕获 Core1 访问异常，前面没有 WDT 重启。413452 字节完整转储通过校验，原始日志及解码已保存。

## 断电恢复后直接异常

原始 PC=0x48184392，历史有效 LOAD PC=0x4818438a，读取地址 0x4ff47840，是 `idle_cb[core][n]` 回调数组内的合法位置。SDK 在 `esp_vApplicationIdleHook()` 读取数组元素时发生 Load access fault，而非通过损坏回调指针进行跳转。MEXSTATUS=0x00102930，BUS_ERR=1，PMP_ERR=0。

硬件状态：`core_timeout_raw=0x30`。按本地 ESP32-P4 rev3 `hp_system_reg.h`，bit4/bit5 分别为 Core0/Core1 DBUS timeout。ICM raw/deadlock 此次均为 0；缓存 access-fail、addrhole、SRAM error raw 也为 0。不要将先前重启现场的 ICM 死锁标志混入本次结论。

Core0 当前为 LVGL，保存的回溯落在显示 SPI 的 `panel_io_spi_tx_color -> spi_device_release_bus -> spi_bus_lock_acquire_end -> esp_intr_enable` 路径；部分底层回溯和优化参数有限，不能把打印的 color/color_size 当作可靠入口实参。安装工作线程正在等待投递给 LVGL 的抬手事件完成。Wi-Fi 和 SDIO 任务在等待，ready=true、scanning=false、error=ESP_OK；设置任务等待队列。没有直接任务栈耗尽证据，LVGL 仍有约 48 KB 栈空间。

## 与 V0.3 比较

基线 commit `12dfc3d` 与当前配置、`tmp/symbols/0.3.0/sdkconfig.h` 的实际宏值已比较：IDF/LVGL 版本约束、CPU 400 MHz、PSRAM 200 MHz、XiP、Cache/PMP 基础配置保持一致。显示 BSP/profile 仍为 SPI、50 行内部缓冲、无 PPA、无双缓冲。LVGL 内部任务栈由 8 KB 增到 48 KB。

后续增加 QuickJS、字体和动态 UI、Wi-Fi/SDIO、安装和设备服务；它们改变了内存布局、执行时序和总线负载，可能触发潜在问题，但“加入后更容易复现”不是具体组件根因证明。单次合法 SRAM 读写超时也不能证明板子损坏、SDK 缺陷或整个架构必须重写。

本地 SDK 已包含官方 `esp_rom_cache_writeback_esp32p4_esp32s31.c` 双次 writeback 补丁且配置启用，不能把发现该历史补丁当作本项目尚缺补丁而重复移植。

## 单变量对照

独立 `build-psram80` 和 `.tools/diagnostics/psram80/sdkconfig` 仅把 PSRAM 从 200 MHz 改为 80 MHz。实际生成配置只相差三个频率宏，Wi-Fi 和所有功能不变。匹配 ELF `d717900729839e9a32c11026c0548055d37a70fea57b865c9788f236e72357a8`，现场 `.tools/diagnostics/device-0410-psram80/`：前四项板上 Unity 通过，第五项发生 HP_SYS_HP_WDT_RESET，复位前没有串口 panic 输出。80 MHz 仍失败，不能把降频当作修复；主 sdkconfig/defaults 保持 200 MHz，后续诊断已刷回 200 MHz。

## 复位前记录与最新现场

上述没有输出的 WDT 现场中，ROM 保存的 Core0 PC 位于 `panic_handler`，Core1 PC 位于 `_panic_handler`。说明复位前已经进入异常路径，不能把无 Guru 输出当成没有异常；不能仅凭这些 PC 判断首次异常源。

增加约 144 字节 RTC no-init 记录，按核心在最早异常入口、读取 MMIO 前保存 CSR/原始异常帧及访问历史，校验后最后提交 magic。重启在 app_main 最前面补打一次，不改 WDT 或双核 panic 仲裁。主机测试覆盖嵌套异常、首条保留、校验失败拒绝和启动清 BSS 后补打。真实 UART 验证已通过。

`.tools/diagnostics/device-0410-retained-v3/` 匹配 ELF `8b7f70ab8968c225fd818e76f77f34648b0c4b7b9c4f9bca1f8dae44e8f35c81`：首次打开 Counter 后、`call_ui(U_OPEN)` 尚未返回即异常，未发送上滑、未截图。Core1 原始 PC `0x4ff2023a`，三个有效 STORE `0x4ff20236/234/232` 向 `0x4ff4f864/860/854` 写寄存器；这是中断入口、切换中断专用栈之前的合法 IDLE1 任务栈。`core_timeout_raw=0x20`，仅 Core1 DBUS。Core0 的 LVGL 在 `wait_for_flushing`。完整 413564 字节转储通过官方校验，重启后 retained v3 补打与现场一致。由此可排除 snapshot 是本次必要触发条件，不能凭 RA 位于 `esp_cpu_wait_for_intr` 断言正好发生在 WFI 唤醒。

## 本地发现但尚不能解释主故障的 SDK 问题

`esp_driver_spi/src/gpspi/spi_common.c` 的 `spicommon_dma_desc_alloc()` 把 `aligned_len` 声明成 `uint8_t`。当前池 76 个、每项 16 字节，对齐后应同步 1216 字节，实际截为 192 字节。这是确切的长度溢出，但两次现场有效 LCD 链均为 8 项共 128 字节、覆盖 32000 字节像素且链内容正确，当前有效链落在已同步部分。V0.3 也使用同一个驱动，暂不能把它认定为主根因。

`DBG_IDLE` 是调试构建的可逆对照：`0` 用官方 idle hook 返回 false 跳过 WFI，`1` 恢复正常；重启默认正常。保留两个核心、Wi-Fi、显示和原频率。它用于检验空闲/中断时序，不能当作节能或稳定性修复。结果以实测记录为准。

## 同一二进制的显示等待对照

后续快照增加两核硬件 PC/SP、记录使能、最近异常 PC 和 cache sync 参数，共 34 个只读寄存器，双核快照 1000 字节。SDK 原本已启用两核 PC 记录；本项目没有新增寄存器写入。对端 PC 是早期采样，不能当作原子捕获的完整对端异常帧。

| 现场 | 条件 | 结果 |
| --- | --- | --- |
| `device-0410-idle-busy2` / `device-0410-idle-normal` | 同一个 `fba02143d3` 二进制，跳过/恢复 WFI | 各 10 轮通过；不支持认定 WFI 根因 |
| `device-0410-native-desktop` | 纯 C 桌面下拉收起，无 JS/snapshot | 30 轮通过 |
| `device-0410-native-settings-2` | 纯 C 设置页中央滚动 | 30 轮通过 |
| `device-0410-native-counter-2` | JS Counter 连续点击，无切换/snapshot | 30 轮通过 |
| `device-0410-peer-normal` | `015a770ff2`，正常 LCD 传输 | Core1 tick hook 读合法 SRAM，BUS_ERR；硬件对端 PC 在 `wait_for_flushing`；同步已完成；另有单独启动阶段转储 |
| `device-0410-peer-no-lcd` | 同一个 `015a770ff2`，仅暂停实际 LCD 传输 | Unity 5 项及 30 轮混合操作通过；11539 次 flush 继续被执行并完成 |
| `device-0410-peer-normal2` | 同一个 `015a770ff2`，重启恢复 LCD，等待无线初始化后测试 | Core1 喂任务看门狗时读取合法 PSRAM，BUS_ERR；硬件对端 PC 仍在 `wait_for_flushing` |
| `device-0410-flush-yield` | `b262c5f5a7`，LCD/Wi-Fi/WFI 均正常，只将 flush 等待改为让出 CPU | Unity 5 项及 30 轮混合操作通过；10238 次真实等待；LCD enabled=1、skipped=0 |
| `device-0410-flush-spin` | 同一个 `b262c5f5a7`，重启后恢复原紧轮询 | 通过 4 轮后第 5 轮发生 HP WDT 复位；RTC 记录 Core1 调度器 BUS_ERR 和 Core0 中断 WDT 异常 |

两个 `015a770ff2` 直接异常中，`CACHE_SYNC_CTRL=0x10` 表示同步已完成，MAP/ADDR/SIZE 只是上次同步记录，不能写成同步死锁。Core0 硬件采样 PC `0x480f1100` 确认在 LVGL `wait_for_flushing`，补足了仅看 TCB 回溯的不确定性。`peer-normal` 的 `decoded-1.txt` 对应首次直接异常，`core-2.b64` 是单独的重启阶段故障，不混为同一现场。

`b262c5f5a7` 的反向对照避免了重新编译造成内存布局变化这一混淆因素。它支持将默认紧轮询的显示等待路径作为当前可重复的修复点；仍不能据此宣称已证明某条芯片仲裁 errata、SDK 所有问题或 Wi-Fi 完全没有间接影响。

## 默认修正

板级 `ouse_board_init()` 在 BSP 的 LVGL 锁内，通过官方 `lv_display_set_flush_wait_cb()` 安装 `ouse_display_flush_wait()`。保持 SPI、DMA、实际屏幕传输、Wi-Fi、双核、CPU 400 MHz 和 PSRAM 200 MHz 不变。等待期间每次阻塞 UI 任务 1 tick；只有原 LCD 完成中断清除真实 `flushing` 标志后才返回，不用提前 `flush_ready` 掩盖问题。默认行为不依赖设备调试开关。

LVGL 9.5.0 没有公开的 pending-flush 查询，板级 helper 明确固定到已测试的私有 display 布局；升级 LVGL 需重新审查。真实 LVGL 主机回归模拟 DMA 在第 3 次让出 CPU 后完成，校验活动缓冲区不被修改/复用，并覆盖同步完成不等待。原 3 个 native 场景和 200 次生命周期回归也通过。

`DBG_FLUSH 0/1/status` 仅用于诊断，允许在同一二进制恢复旧紧循环或启用新等待；`DBG_LCD 0/1/status` 仅用于暂停/恢复实际传输。最终正常测试保持 LCD 开启，不通过跳过传输获得稳定结果。
