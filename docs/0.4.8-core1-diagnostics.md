# 0.4.8：Core1 操作崩溃诊断版

这是现场捕获版本，**根因尚未定位，不能视为死机修复版**。CPU 400MHz、PSRAM 200MHz、XiP、双核、USB 波特率 115200 和应用/设备服务策略保持原样。

## 本次已经确认的事实

附件 cb07a2f7-6f27-46a7-9218-6e528e92ac2c 的崩溃日志与保存的 0.4.7 ELF 完全匹配，ELF SHA256 为 `9140e957ef06277c05eb` 开头。完整原始日志、ELF/MAP/配置及分析保存在 `.tools/diagnostics/9140e957e/`。

日志已出现 Station started 和 StaScanDone，说明之前强制版本查询阻塞初始化的问题已越过；这份日志尚未证明连接 AP、获得 IP 成功。约 11.77 秒打开 `user.usb-counter`，用户确认点击/滑动界面后崩溃。

Core1 的 Load access fault，MCAUSE=5，打印 MEPC=0x4ff32786，对应 FreeRTOS 的 `xTaskIncrementTickOtherCores` 读取就绪列表计数；打印 MTVAL=0x4ff3c548，在匹配 MAP 中为内部 BSS 的 `pxReadyTasksLists`。SP=0x4ff3d2f0 位于该版本 Core1 ISR 栈范围内，目前没有足够证据判定栈溢出、手势越界、USB、Wi-Fi 或 PSRAM 是根因。

ESP-IDF 6.1 对 P4 异步总线错误可能用历史失败 PC 改写打印的 MEPC，未同步回滚其他寄存器。因此不能仅用当前 A2、MTVAL 和反汇编认定历史访存就是这个有效内核地址，也不能据此修改 FreeRTOS 或关闭内存保护。

## 本版新增什么

复用归档中已验证的早期异常捕获模块，生成 ESP-IDF panic 源码的产品副本，不编辑 SDK 安装目录，不接入 Brookesia：

- 在 panicHandler / xt_unhandled_exception 第一处新增调用中，先记录每核首次异常，早于 SDK 开缓存或改写 PC。
- 记录原始 PC、异常帧、MEXSTATUS / MHINT、LOAD / STORE 历史 PC 与实际地址，以及 PMP / PMA 原始配置。
- 捕获过程只读 CSR 和写固定内部 DRAM，不分配内存、不取锁、不打印、不写 CSR。
- 标准 panic 日志前输出 `[OuseFault v1]` 至 `[OuseFault end]`。
- 启用官方 UART core dump，包含内部 DRAM/heap 和任务现场，使用 4096 字节内部 dump 栈；转储过程中每完成一块继续喂 SDK panic 看门狗，避免正常传输尚未结束便复位。看门狗未被永久关闭。

捕获结构占 728 字节内部 RAM，panic IRAM 和 core dump 另有开销，以实际编译大小为准。后续源码核对纠正：本地 IDF 6.1 的 `heap_caps_walk(MALLOC_CAP_8BIT, ...)` 会包含已使用的 PSRAM 堆，因此本版转储可能达数 MB，先前“仅内部堆”的描述不准确。后续准备的产品过滤改为 `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT`，不改变早期 CSR 捕获。操作发生的线程与共享对象状态可结合 core dump、MAP 和原始 CSR 判断。

## 烧录和下一次日志

只更新 `tmp/ouse_core_desktop.bin` 到 **0x10000**，保留原有设置和 BPK。启动应显示 `Fault diagnostics v1: early P4 CSR snapshot + UART internal DRAM core dump`。

串口继续使用 **115200**。正常使用并重复之前会出错的点击、滑动；如果再次异常，保留从 Guru Meditation 开始，直到完整 `CORE DUMP END` 或自动重启的原始日志。转储可能持续一分钟甚至更久，期间不要手动复位；即使没有 END，已有的 OuseFault 段仍需保存。关闭 USB 安装工具后再打开串口监视器，保证同一个 COM 端口只由一个程序读取。

此轮没有烧录或重启板子，也没有在板子上引入截图/远程触摸服务。

## CH343 和图像传输后续方案

CH343 可以尝试 921600 波特率，并在实机校验后再考虑更高速度。两端必须协商切换，空闲/故障时恢复默认速率，电脑安装工具也需支持指定速度；不能只改其中一端。当前保留默认速率用于同条件捕获崩溃。

320×480 RGB565 为 307200 字节。921600、8N1 的纯数据理论上限约 92160 字节/秒，完整原图至少约 3.33 秒，实际还会受帧封装和确认影响。后续图像应采用分块二进制传输，避免现有十六进制格式翻倍带宽。

单张界面可按需压缩 JPEG，连续 JPEG 才构成 MJPEG 预览。可以评估 P4 JPEG 硬件编码器；需适配输入格式、DMA 对齐、独立后台编码任务和有界帧缓存。JPEG 有损，会影响文字边缘，精确检查 UI 可另提供无损截图。截图在 LVGL 任务生成，编码和传输在后台，只保留有限帧、允许丢弃过期帧，避免慢串口阻塞界面。

这些传输改进适合下一步实施，本版只增加崩溃诊断，不把新编码/模拟触摸路径与原故障混在一起。
