# Core 0.24.0 音频混合与焦点

原生 API 27，BPK API 仍为 1。保持现有 PCM16、单声道、16 kHz 的解码与 I2S 链路，不增加音频线程、DMA 通道或全曲缓存。

## 行为

- 唯一媒体流加唯一提示流，由同一个音频线程混合后写声卡。
- 短提示音把媒体 PCM 压到 50%；持续提醒与系统闹钟压到 25%。32 ms 增益过渡，结束或取消后平滑恢复，不改变用户音量设置。
- 音乐暂停时仍可响提醒，但不消费音乐 PCM；缓冲或音乐结束时也可以继续响提醒。
- 提示流优先级：系统闹钟 > 应用持续提醒 > 普通提示音。低优先级不能抢掉持续提醒；同优先级不同应用不能相互抢占。
- RAM/SD 录音期间拒绝应用提示音；系统闹钟延后到录音结束再输出，避免扬声器声音进入录音。持续提醒中拒绝新录音。
- USB 双工保持独占，不混入麦克风或 USB PCM。持续提醒时拒绝新 USB 会话；USB 占用期间普通应用提示请求失败，系统闹钟保留原有抢占 USB 行为。
- 普通后台通知横幅出现时尝试短提示音；前台自身通知、持续音乐通知不会因此发声。静音与主音量始终有效。

## 脚本接口

`Ouse.audio.alert()` 需要 manifest 的 `notifications` 能力，返回任务 ID 或 false；成功后按半秒响、半秒停持续提醒。调用 `Ouse.tasks.cancel(id)` 停止自己的提醒，关闭应用也会取消。

`Ouse.audio.testTone()` 保持原接口，现在进入混合提示流，不抢占媒体任务。

`Ouse.audio.get()` 新增 `alertActive`、`alertTaskId`。`Ouse.audio.stop()` 只取消调用应用自己的音频任务，返回停止请求任务；不再误停其他应用的音乐，底层取消仍由音频线程处理。原生系统停止接口仍为全局停止。

## 应用影响

- 倒计时：需要更新 BPK，改用持续提醒接口；保留到时通知和确认框，音频忙时重试。
- 音乐、相册、录音机：无须重写；继续使用唯一媒体会话和现有录音服务，混合/避让由内核执行。
- 闹钟：应用不需要更新；内核闹钟的响铃任务进入混合流。
- 接口测试、其他使用 testTone 的应用：旧包兼容；停止音频改为实例隔离。
- 多个音乐/视频应用仍不能同时作为媒体流混音。现有媒体服务维持单会话/所有者隔离，其他播放器需要先完成原会话停止，并非无限路混音或自动排队播放。

## 验证

`python tools/test-ouse-audio.py --mixing` 覆盖真实设备服务和生产混合代码：压低/恢复、样本饱和、优先级、媒体任务不被取消、录音互斥、跨实例停止隔离、关闭清理。常规音频、录音格式、SD 录音、权限和 BPK 检查继续执行。

最终固件 SHA256：`006d51cebb146d045daa3e43dba51efca2c0ea6317102ddc1bcb65d24a056d93`，5,391,232 字节。已通过远程电脑的实体 COM5 更新 `0x10000` 应用分区并校验；不擦除启动、分区表、NVS 或应用存储。

真机临时测试包确认：短提示音结束后媒体任务 ID 不变；持续提醒时媒体仍播放；暂停媒体期间提醒任务继续运行且播放进度不变；确认只取消提醒，原媒体任务恢复。临时测试包已移除，结束时 errors=0、DBG_CHECK ok=1，内部空闲约 85,867 字节。

全量旧检查不计为全部通过：`test-ouse-core.py` 的主机夹具缺少 `ouse_tasks.h` include 路径，`test-ouse-services.py` 的 net 夹具缺 `ouse_channels_init` 链接实现。相关音频/任务内核专项与实际 IDF 固件构建通过；本轮未修改这两个与混音无关的夹具问题。
