# 荒野生存：JS / C++ 实机配对测试

2026-10-26，同一台 COM10 设备，同一份 0.46.0 / API 48 固件。
测试入口：`python tools/benchmark-survivor-device.py --port COM10`。

## 方法与适用范围

临时 BPK 直接使用生产 `engine.js` 的 JS 回退分支和 C++ 分支，以及生产 `render()` / `renderHud()`。JS 与 C++ 共用同一固件、画布、屏幕、资源和 UI。测试完成后删除临时包，正式游戏的存档不参与测试。

- 横屏 480 × 320，本次设备使用全面屏手势（`navigation=0`），全屏内容区为 480 × 320；两边音效均关闭。脚本保留设备原导航模式。
- 普通负载：8 个敌人、8 发子弹；压力负载：24 个敌人、32 发持续穿透弹。
- 固定种子、角色、武器和伙伴。敌人固定位置且不死亡，子弹按确定的轨迹反复回放；弹药寿命、命中掩码和穿透次数在每次回放前复位。场景有持续变化，避免相同画布命令被复用而高估动态显示性能。
- 这是受控负载：穿透次数设为 100、伤害为 0，防止实体数量在测试中减少。它不是普通玩家战斗录像。
- 每次游戏帧执行一个 `1/60 s` 模拟步，确保同序号的两边画面和完整状态一致。正式游戏根据真实帧间隔补步，因此这里的 FPS 是固定负载回放值，不是所有实战场景的保证帧率。
- 每组先做 120 个独立模拟计时步，再预热 30 帧、测量 180 帧；比较原 25 FPS 上限和 `maxFps=0`。重复三轮，第二轮反转后端次序。
- 分帧计时使用设备 `Date.now()`，分辨率为 1 ms；累加后求平均，不把单次 0/1 ms 差异当作结论。
- 模拟耗时包含整个 `game.advance()`，包括 JS 对象打包、ArrayBuffer 访问、原生调用、结果回写及其余 JS 游戏逻辑；不包含场景复位和绘图。
- 帧率按完成的系统帧回调计数，与游戏内 FPS 的口径一致。LCD 传输计数另从 UART 提取；物理面板扫描率不能等同于游戏帧率。
- 每组结束比较两种后端完整的 `game.state`，而非仅比较击杀数或截图。

测试没有关闭固件的脚本执行时限。试跑时发现测试初始化/批量循环和日志长度的限制，已将初始化、采样、结果序列化分开调度，并减少临时对象；失败试跑不计入最终结果。

## 最终结果

以下为三轮中位数；模拟耗时采用动态绘制期间的整段 `game.advance()` 计时，包含数据打包及结果回写。

| 负载 | 帧率上限 | JS FPS | C++ FPS | FPS 增幅 | JS 模拟 ms/步 | C++ 模拟 ms/步 | 模拟耗时下降 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 8 敌人 / 8 子弹 | 25 | 18.20 | 18.99 | 4.3% | 6.09 | 5.09 | 16.3% |
| 8 敌人 / 8 子弹 | 无 | 18.27 | 19.14 | 4.8% | 6.17 | 5.13 | 16.9% |
| 24 敌人 / 32 子弹 | 25 | 8.32 | 11.01 | 32.3% | 41.33 | 14.39 | 65.2% |
| 24 敌人 / 32 子弹 | 无 | 8.38 | 11.05 | 31.9% | 41.33 | 14.36 | 65.3% |

不限帧的三轮范围：普通负载 JS 18.16～18.28、C++ 19.01～19.16 FPS；压力负载 JS 8.375～8.402、C++ 10.92～11.10 FPS。压力负载 P95 帧间隔从 134 ms 降至 112 ms。

LCD 传输计数按回放期间内部的计数差、采样时长加权汇总：普通负载 18.22 → 19.20 帧/秒；压力负载 8.39 → 11.14 帧/秒。各后端有效采样约 15～46 秒，来自异步日志，不能与游戏回调 FPS 的小数逐位比较，但趋势一致。没有把游戏循环空转速度当作面板显示速度。

单独运行模拟、不同时绘图时，普通负载 4.63 → 4.25 ms/步，压力负载 35.00 → 13.51 ms/步。与绘制期间的计时不同，说明线程/内存/提交竞争也会影响实测耗时。

数据支持的结论：此次迁移在实体密集时更有效；整局帧率增幅远小于桌面端单独计算内核的约 280 倍。相同场景中取消 25 FPS 上限没有带来大幅提升，因为这些动态负载已经低于 25 FPS；绘制和系统刷新链路仍占明显时间。

### 验证与证据

24 组回放共 4,320 个计量帧、720 个预热帧、2,880 个独立计时模拟步全部完成；每对后端的完整状态相同，最终回放 UART 没有脚本错误日志。

原始数据及汇总：`.tools/survivor-device-benchmark-v7/result.json`；UART 及动作证据：`.tools/diagnostics/device-20261026-103100-907208/`。同一份固件 ELF SHA256 为 `2c1acc6b31a6fc22360452d0c5b7eb5edd53e6082eead64a8e7a85fd909d4924`。

测试脚本最初的末尾断言要求全局 `errors=0`，因此在全部回放完成后把前六次测试夹具调试留下的累计 `errors=6` 判为失败。该计数在固件中为全局累计值，卸载应用不会清零。已修正脚本为比较前后计数；没有把该次命令描述为零错误计数通过，也没有为了清零而重启设备。有效回放数据来自最终完整 UART；后续正式包验证另采前后错误基线、检查堆完整性，记录在同结果目录的 `uncapped-device.json`。

## 解除帧率上限

正式游戏 2.1.1 使用 `createGameRuntime(tick, 0)`，默认解除原 25 FPS 人为上限，仍由 `Ouse.timers.requestFrame()` 驱动，没有忙循环或积压帧。

`tools/test-survivor.cjs` 增加了连续三个 16 ms 帧回调均推进游戏的检查；同时保留武器、关卡、暂停/恢复、界面及生命周期回归测试。固件二进制不因游戏取消上限而变化。

2.1.1 已安装到设备，BPK SHA256 为 `284fd38dbfecdf7232e92c6d55d1b1e5b23aea88f5c805a36abbaa0908fb8bd3`。实际进入原用户配置的游戏，报告 `SURVIVOR_ENGINE native`，两个状态样本为 28 / 20 FPS，说明可超过原上限且随实战场景变化；它们不参与上表配对结果。运行前后全局累计错误均为 6，没有新增错误，`DBG_CHECK=ok=1`。临时测试包均已删除，恢复竖屏、原 34 个注册入口，以及相册前台和设置后台。串口已释放。
