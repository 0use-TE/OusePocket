# 0.21.1 camera / Wi-Fi memory-pressure fix

## Evidence

The retained UART test log from 0.21.0 shows OV5647 streaming and recording
starting, then `assert failed: sdio_push_data_to_queue sdio_drv.c:928
(pkt_rxbuff)`. That assertion follows a failed internal DMA allocation in the
Hosted Wi-Fi transport; it is not a camera-sensor detection error.

A separate 90-second 0.21.0 preview probe kept internal free memory at 40,955
bytes after startup, and returned to 48,819 bytes after camera close. PSRAM was
also stable apart from small transient script allocations. This probe did not
show a continuously growing preview leak; it does not rule out all longer-term
or concurrency faults. The assertion proves one failed allocation, not that
every reported freeze has the same cause.

## Changes

- Enable the SDK-supported PSRAM stacks for Hosted tasks. Transport DMA buffers
  and task control blocks remain internal; PSRAM XIP and external-stack support
  were already enabled on this product.
- Reduce Hosted SDIO RX/TX queue depths from twenty to eight.
- Keep at most four returned buffers in each Hosted DMA pool. Excess idle
  buffers return to the heap rather than retaining the historical burst peak.
- RX streaming allocation failure waits at most twenty five-millisecond retries,
  then discards the remaining stream instead of asserting. TX already has a
  normal allocation-failure cleanup path; remove the assertion that bypassed it.
- Streaming DMA-buffer growth failure unlocks transport and retries later;
  payload-copy allocation failure returns the owned packet buffer and drops the
  packet instead of aborting the system.
- Free the allocated RX buffer when rejecting an oversized stream packet.
- Require 32 KiB internal free memory before starting recording, and 16 KiB after
  encoder allocation. Insufficient resources fail the request without aborting.
- Add bounded ROM allocation-failure diagnostics: first sixteen failures, then
  every 128th. The callback does not allocate memory.
- Restart camera preview after display sleep/wake without silently attempting
  to acquire camera hardware while asleep or while the application is paused.
- Active recording and video playback inhibit automatic idle screen sleep;
  manual screen sleep and background/close still release resources. Plain
  unused preview may sleep normally and restarts when the user wakes the screen.
- Publish a saved recording path only after successful final rename.

The Hosted changes are generated build overlays owned by the product, with
normalized SHA-256 guards for both reviewed upstream source files. Managed
dependency files are unchanged. An upstream source change fails configuration
until the overlay is reviewed again.

## Regression checks

The camera app is now photo-only at the user's request. Its recording mode,
record timer and record/stop handlers are removed. The shutter remains centered
and the left album shortcut is retained. This app-only change requires replacing
`camera.bpk`, not reflashing firmware. Gallery video thumbnails, playback and
replay remain unchanged; existing AVI files are not deleted. Native recording
APIs remain in the firmware for compatibility but are not called by the camera.

`tools/test-hosted-memory.py` compiles the generated real RX/pool functions and
checks persistent OOM, transient recovery, bounded retries, malformed-packet
cleanup, and returning excess cached buffers. Existing driver, AVI, app-logic,
and production BPK schema/QuickJS checks cover the camera/gallery integration.

## SD write compatibility

Physical tests also reproduced SD write timeouts with more than 73 KiB internal
RAM still free. Lowering the SD clock and limiting file writes to 4 KiB alone
did not fix that second failure. A shared recursive product-level bus gate now
keeps complete SD memory operations/card initialization atomic against Hosted
SDIO commands, and SD writes use single-sector CMD24 transactions rather than
multi-sector CMD25 on this board. The gate uses static internal semaphore
storage, wraps the SDK entry points at link time, and does not modify SDK files.
The SD clock is conservatively limited to 10 MHz and bounce chunks to eight
sectors. Neither the card nor existing user data is formatted or erased.

The combined single-sector build completed a roughly 40.6-second silent
1280x960 recording, 55 frames, 6,304,084 bytes, CRC32 d78bd219. This is about
1.35 fps on the current card/compatibility path, **not** the nominal 10 fps
target; stable recording is verified but high-frame-rate performance is not.
Preview and recording currently share the native worker, so synchronous SD
writes can reduce preview cadence while recording. This limitation is not a
claim of phone-like video performance.

Direct video-thumbnail selection, playback to completion, replay and returning
to the grid passed on the physical device. Runtime reported zero script errors
and heap integrity check returned ok=1. A first test had selected a photograph
rather than a video; its missing replay button was a test-selection failure,
not evidence of playback failure. Tests now select a video-marked tile.

Firmware BIN SHA-256:
`7efc0b60c8fb59daf8bcf0360d61ac03a133d08cb423dbaf0be26dee026542df`.

Two earlier idle tests were interrupted by unexpected foreground changes. They
are not counted as successful idle tests, and the user denied manually causing
the first change. Debug builds now log physical/remote touch starts, camera and
gallery click targets, display sleep/wake and navigation call sites so future
events can be attributed rather than assumed to be user input.
